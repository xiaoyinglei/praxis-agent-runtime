## 1. 因果链，不是五个彼此独立的症状

工具批量返回 → 活跃历史超出人为设定的 14 KB → 整批读取被语义摘要替代 →
下一次请求仍含用户“首先读三个文件”要求，但已无原始读取交换 → 模型多次再次读取 →
重复摘要消费累计预算 → 输出额度被挤到 96 token → 摘要不完整，Turn 失败。

前三个箭头和最终失败有请求/落盘证据；“结构丢失导致模型回读”只是有对照支持的机制假设，
不是已证明的唯一根因。assistant 摘要角色已有真实失败反例，不能将角色适配当作解决方案。
运行时也不能因模型测试断言失败而自行宣告完成：本次 `verify.py` 添加了规范没有要求的
对象身份不相同断言，Agent 原本还需要判断并修正该验证；外部功能断言通过不意味着任务已完成。

## 2. 已确认的设计缺陷与证据

### 计量层：把检索分词单位作为 token 预算依据

`core/llm_registry.py:424` 为模型选择 tokenizer，`modeling/tokenization.py:238` 在后端不可用时
静默退到 simple。`text.py:144` 的 simple 仅数英文数字串和汉字，不统计 JSON 标点，
长数字串仍算一个单位。`harness/model_adapter.py:669` 将 count 的结果直接用于输入上限和预留。
该分支存在是源码事实；旧快照未落盘 tokenizer backend，不能声称已证明当次实际后端。
但当次预算估算严重失真已有独立证据：

| 请求 | 持久化估算输入 | Provider 实际输入 | 比例 |
|---|---:|---:|---:|
| 第一次摘要 | 3870 | 13200 | 3.41 |
| 第二次摘要 | 4499 | 14716 | 3.27 |
| 最后摘要 | 2325 | 5673 | 2.44 |

来源：`deepseek-session-code-20260923-232844/session.db` 的 model_operations 与
context_summary_response usage；汇总在 `evals/context_management/offline-root-audit-20260923.json`。
序列化一致和 wire hash 相等，只证明“算的是相同内容”，不证明计数方法可靠。
实际 usage 结算虽正确，却无法补救发请求前的严重低估。

处置：先明确精确 tokenizer / 估算 / 不可用的计量契约、记录计量来源，离线回放现有请求评估偏差；
不能直接给现有 count 乘一个从该样本拟合的常数，也不能全局改动 RAG chunking 来修运行时预算。

### ACI 与窗口：只有单工具上限，没有批量返回的活跃窗口预算

项目不是完全没有输出限制：`tools/executor.py::_bound_model_output` 限制单工具输出；
`read_file` 默认读取 16000 字节，并有分页。缺口是这些上限没有与该次活跃上下文剩余容量及
并行批次总量协调。三个分别合法的结果可共同挤掉整个当前工作单元。
`context.py:300` 当最近一组本身大于总字节上限时直接返回保留 0 条，随后进入全文摘要。

Codex 固定参考 `context_manager/history.rs:340–360` 在结果进入活跃历史时应用输出截断策略，
与 `compact.rs:683–758` 的历史摘要替换是两个边界。不能只借用后者而忽视前者。
也不能宣称 Codex full compact 总保留最近工具组：该本地分支保留受限用户消息加摘要。

处置：原始证据持久化与模型可见输出分离；明确单结果和批次的可见预算、截断标记、原文入口，
在既有 Executor/ContextManager 边界内解决，不新建第二套执行器。截断内容不得冒充已进入摘要。

### 压缩规划：预算上有余数，不等于有可行的压缩计划

`turn.py::_prepare_compacted_step` 将输出额度减至剩余预算分摊值，只检查 cap >= 1。
最后一次 `sdk-request-11.json` 要总结约 17 KB 历史，max_tokens 实际为 96；Provider 也正好
输出 96 后截断。一次续跑预留并未保证摘要可用，也未保证后续修正/验证能进行。
此外 `min(..., byte_limit)` 同时比较 token 与 UTF-8 字节，不能推导输出一定能放回历史；
提交前复测能防止错误提交，却不能收回已花费的调用。

处置：压缩是有失败可能的状态转换，不是必定成功的格式变换。分别定义窗口预算、总花费预算、
摘要额度、替换后的空间收益。不要把 96 改成另一个凭空的“最小 token 常数”；先根据明确策略
拒绝预算不足的计划，保留原上下文和失败原因，再验证正常容量与压力容量下的收敛行为。

### 恢复与投影：版本补丁已经掩盖合同不一致

当前实验 v5 在 retained=0 时又自行回放部分 assistant/tool，并用引用替换结果；这改变了
“保留 0 条”的含义，也影响 protected items、summary source、归档覆盖与恢复投影四处逻辑。
离线回归现有 5 个失败：包含孤立工具结果、候选不再缩小、旧测试与新保留语义冲突。
不能把这些一律改成新期望值来获取绿色测试。

处置：暂不扩展 v5；先明确“原样尾部、裁剪结果、已摘要历史”的互斥/组合合同，选定后再作
一处语义变更及完整链路验证。历史落盘格式继续兼容；不擅自清理已有实验代码与数据。

### 验收：成功执行 shell 不等于验证成功

`session_code_live.py` 旧 gate 将任意成功 run_command 算作 model_ran_verification。
232844 的 `ls -la` 成功、`python3 verify.py` 失败，但该字段为 true。
本轮已改为 canonical tool_call 的确切验证命令与成功 operation 按 call ID 关联；
增加“目录成功+验证失败”和“echo 验证命令”反例。原报告不改写，离线复判单独保存。
复判将该运行的验证 gate 改为 false；232318 第一阶段仍为 true。

## 4. 2026-09-24 已实施的第一批根因修复

- `TokenAccountingService.count_for_budget` 与检索/分块 `count` 分离。没有 tokenizer 时，
  请求预算保守按 UTF-8 字节估算，不再使用忽略标点的词数；可用 tokenizer 继续使用原编码。
  Adapter 窗口检查、资源预留及 Gateway 准入共用该入口。请求快照记录 `count_source`，
  自定义计数器仍兼容并标为 `external_counter`。这不是 provider 精确 token 保证。
- Turn 不再根据累计预算余数缩小摘要输出额度。按配置的摘要额度及续跑输入容量计算整个计划，
  付不起则零摘要调用失败，保留原历史。UTF-8 字节余量不再与输出 token 直接取最小值；
  续跑输入预留使用受限的序列化摘要空间，不能把摘要输出 token 上限当成续跑输入增长上限。
- 停止生成 v5 的隐式工具回放，恢复 `retained_tail_messages=0` 的明确含义。
  最近完整交换原样保留或完整进入摘要来源，不额外伪造结果内容；已有 v5 读取兼容保留。
  这撤销的是没有真实验收支持的策略，不是删除原始证据或撤回用户工作区。

新增反例验证计数器降级、Adapter/Gateway 预留一致，以及“能付输入却付不起完整摘要和续跑”
时没有任何模型 operation/dispatch。原五项回归已消除；正常摘要、原文检索、落盘恢复回归通过。
本轮还检查了 Harness、工具执行/取消和 Gateway 回归。测试用于验证边界，不替代真实任务验收。

## 5. 2026-09-28：摘要输入阶段错配的离线复现与修复

原失败现场为 `deepseek-session-code-20260928-132742` 的第二个 Turn。
预算按 turn_id 结算，没有把第一轮用量重复扣入第二轮；当时正常可用预算为 84,862 token。
问题在 ModelAdapter 把上下文压缩送到普通 `llm_summarize` 阶段：Agent 可接收 64K 输入，
普通摘要却只允许 16K。51,298 字节、31 条历史经过完整工具组边界拆分，成为
5 份输入加 4 次合并；预留 126,559 token，因而在零摘要调用时拒绝。
这不是 provider 拒绝，也不是服务端 usage 精度问题。

固定参考 Codex `compact.rs:260–295` 克隆历史后通过同一 turn_context/model 发起压缩；
没有在这条路径套一个无关普通摘要任务的小输入窗口。本项目的具体实现是自主设计：
新增 `context_compaction` stage，缺省从 agent_step 继承输入上限、从 llm_summarize
继承输出上限，安全余量取两者较大值；Gateway 继续扣除模型窗口内的输出和安全余量。

仅解释拒绝算式；根因是阶段错配引起不必要的拆分，而非应随意缩小合并预留。
