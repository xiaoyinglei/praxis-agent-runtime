## 值得直接指出的问题

| 现有设计 | 问题 | 成熟实现给出的方向 |
| --- | --- | --- |
| 模型窗口触发压缩，加最多 8192 tokens 的固定收尾预留 | 大窗口不等于累计预算充足。每轮反复发送长历史，会先耗尽总预算，连最终答复的输入都付不起 | 请求前后检查实际上下文；为压缩与后续请求留空间，累计用量不随压缩重置 |
| 用工具名和命令形式识别通用“验证” | 只能证明某类检查发生过；运行 pytest 不等于覆盖用户要求，读取文件也不等于行为正确。正反两个方向都存在误判空间 | 把循环结束、执行事实、显式验收结果分开；阻断时反馈具体可执行原因 |
| 建议显式断言，但完成门永远不接受 assertion | ACI 自相矛盾。模型照做仍无法收尾，继续消耗长输入预算 | 只推荐现有契约真正支持的补救方式；不能虚构文件覆盖来使断言过关 |
| 恢复历史时沿用新进程默认能力开关 | 先启动 MCP 再恢复边界已经太晚 | 在资源初始化之前协调历史能力与当前权限，所有入口共享限制 |
| 返回对象默认填写 0，但实际执行没有提供指标 | 测量缺失与确实为零混淆，影响诊断和评测 | 在执行边界测量、持久化；未知值明确为空 |

第一阶段保留的旧 `workspace_change` 完成门仅验证
“有实际修改及修改后的受支持检查”，不能充当通用任务正确性裁判。
解析更多命令或增加任务关键词规则不会解决这个问题。已有 `CompletionGate` 接口
允许接入明确的项目验收；第二阶段已完成下述重构。旧 Turn 的冻结接受标准继续保留，
没有把模型自述提升为权威。
同样，没有将某一评测产物已经通过，转写为原生 Turn 必须成功。

## 本轮实际采用的机制

1. `TurnExecutor.run_turn` 在完成真实序列化测量后，检查普通剩余预算是否还能容纳
   当前请求及另一次同等规模请求。若不足，提前进入预算压力，并通过已有摘要规划器
   尝试压缩。摘要树和续跑总量必须整体支付得起才允许调用模型；不提高原预算。
   两请求估计用于调度，不是对未来工具输出大小的保证。
   摘要不可行时保留原历史，尝试能支付的诚实答复；不绕过完成门。
2. `Session.open` 在发现资源之前应用冻结的 MCP 禁用字段。当前禁用和禁止项继续收紧。
   CLI 和 SDK 共享此路径，见 [恢复契约](runtime-recovery.md)。
3. 模型派发使用单调时钟测量。工具沿用执行器已有 trace duration，写入带 fencing 的
   原有 outcome 事件；用持久化执行次数计数。恢复、结果协调和重建不会把一个结果重复计数。
   SDK / CLI 未测量的总耗时、启动耗时和 schema 字节数为空 / unknown。
   `ResourceUsage` 是整数资源账本，原有未采集维度的 0 不代表实际用量已知；不要将其当作
   完整性能遥测或免费证明。失败/未知模型调用的账本 exposure 与已知 token 用量仍分开。
4. 成功断言且目标未被证明时，反馈 `assertion_targets_unattested`，明确限制与可行的下一步。
   没有增加 Python audit 推断：audit 的 open 事件在打开失败时也会发生，不能证明成功读取。

## 异步接口失败的归因

原 cancel-async-tasks 补跑有 9 个请求，0 次压缩。逐一检查冻结请求的 user message，
9 次均保留原始 async run_tasks 要求。因此已有证据不支持“压缩丢失接口约束”的归因。
这是模型实现及其自测覆盖不足；本轮没有加入函数名、asyncio 或题目专用提示规则。

真实评测使用新冻结 wheel，原题面、同样的 200 步和 1200000 tokens 上限。
源码清单、测试日志与新运行保存在 `evals/public_benchmarks/artifacts/runtime-repair-20261016-r1/`，
正式官方结果和原生终态分别记录。旧快照、wheel 和成绩均保留。

新压缩题实测还暴露了另一项恢复能力限制：第 2 次请求的 32768 个输出 tokens
全部用于 reasoning，没有产生可用完整步骤，Runtime 以 `model_response_incomplete` 终止。
Claude 快照 `src/query.ts:1223–1248` 对这种已知截断采用有次数上限的继续路径；
本项目当前直接失败。值得借鉴的是有界恢复、状态持久化与不执行不完整工具调用，
而不是简单照搬它的输出上限升级。本轮未把这项新能力混入已有修复，原始失败与官方 0 分保留。

## 第二阶段：完成契约替代通用测试猜测

新建 Turn 使用 `completion-v2`，CLI 与 Python SDK 共用同一策略：

- 默认允许模型自然结束，结果为 `validation_status=not_evaluated`。自然结束不等于任务验收通过。
- `require_workspace_change=True` / `--require-workspace-change` 只检查真实的工作区修改，
  结果范围为 `workspace_change_recorded`，不再根据测试命令形式推断任务正确性。
  新契约也不再因为修改前已经读取 12 次而屏蔽检查工具；步骤、tokens、费用等资源预算继续生效。
  旧的读取次数限制只随未版本化的历史契约恢复，不能用来迫使新任务提前修改。
- `acceptance_command="..."` / `--acceptance-command "..."` 明确指定用户验收命令。
  它必须通过普通 `run_command` 在工作区根目录实际执行；最新一次必须成功，
  且发生在本任务及同工作区子孙任务的最新修改之后。其他命令、自述和子代理自行运行的检查
  不能代替父任务的验收。验收本身产生的构建产物允许属于同一次检查。
- 命令、策略版本及原预算随 Turn 冻结；恢复、压缩和重开进程不替换契约，
  权限仍按普通工具审批与当前限制执行。命令引用的脚本内容及依赖没有被自动冻结，
  因此成功只证明该命令当次执行成功，不能宣称一般正确性。
- 未版本化的旧 Turn 继续走旧完成门，历史结果不重算。

子代理修改的归属由持久化预算分配关系确认，同工作区才纳入父任务；跨线程顺序使用全局
rollout `record_id`，避免把每个 Turn 内的局部序号混在一起比较。复查中发现的
“先验收、后子代理修改、仍通过”和“只有子代理修改却判未修改”两种错误均有回归覆盖。
失败并发生部分写入的子任务同样会使旧验收过期。

这个边界借鉴上述 Codex 自然结束与 Stop hook 的职责分离、Claude 具体阻断反馈的机制。
没有扩大通用命令识别器，也没有新增题目或工具顺序规则。

第二阶段额外覆盖任意自定义验收命令、cwd、较晚失败覆盖较早成功、修改后的过期验收、
子孙任务、伪造关联、无关工作区、projection 重建，以及公开 CLI / SDK 的真实执行和审批恢复。
